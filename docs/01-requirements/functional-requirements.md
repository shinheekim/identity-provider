# 기능 요구사항 (Functional Requirements)

## 1. 개요
본 문서는 인증 서버(Auth Server)의 기능 요구사항을 정의한다.  
모든 인증 기능은 JWT 기반으로 동작하며, Access Token과 Refresh Token을 사용한다.

현재 개발 단계 기준으로 M3 인증 기능은 개발 완료 상태이며, 로그아웃은 develop에 반영된 상태이다.
M4에서는 일반 로그인 ID와 이메일을 분리한 회원가입 정책, 이메일 인증, 사용자/계정 관리, 소셜 로그인, 소셜 계정 연동/해제, 보안 정책 정리를 우선 진행한다.

---

## 2. 인증 기능
### 2.1 회원가입

- 사용자는 loginId, email, Password를 이용하여 회원가입할 수 있다
- 회원가입 전 이메일 인증을 완료해야 한다
- `loginId`는 로그인 ID이고, `email`은 인증된 연락 이메일로 분리한다
- 회원가입 시 사용자 식별 정보(Identity)를 생성한다
- 동일한 ID(또는 이메일)는 중복 가입할 수 없다
- 비밀번호는 암호화하여 저장해야 한다
- 회원가입 완료 후 `emailVerified = true` 상태가 되어야 한다
- 회원가입 완료 후 로그인 가능 상태가 되어야 한다
- 필요 시 회원가입 시점의 기본 상태값(활성/비활성)을 부여할 수 있다

---

### 2.2 일반 로그인

- 사용자는 loginId와 Password를 통해 로그인할 수 있다
- 로그인 성공 시 Access Token과 Refresh Token을 발급한다
- 로그인 실패 시 적절한 에러를 반환한다
  - 단 일반 로그인시 비밀번호가 틀렸거나 사용자 아이디가 없는 경우 유추가 불가능하게 동일한 에러를 반환한다.
- 비밀번호는 암호화되어 저장되어야 한다
- 이메일 인증이 완료되지 않은 계정은 로그인할 수 없다
- 비밀번호를 5회 연속 실패하면 10분 동안 로그인을 제한한다
- 로그인 성공 시 비밀번호 실패 횟수와 잠금 상태를 초기화한다

---

### 2.3 소셜 로그인

- 사용자는 외부 플랫폼을 통해 로그인할 수 있다
- 지원 플랫폼
    - 카카오
    - 구글
- 소셜 로그인 성공 시 내부 Identity와 매핑된다
- 최초 소셜 로그인 시 회원가입 처리 또는 계정 연동 처리를 수행한다
- provider가 검증된 이메일을 제공하고 해당 이메일의 기존 계정이 존재하면 기존 계정과 자동 연결한다
- provider verified email과 일치하는 기존 계정이 없으면 자동 가입하지 않고 회원가입 또는 기존 ID 로그인 후 소셜 연동을 유도한다
- provider 이메일이 없거나 검증되지 않은 경우 M4에서는 자동 연결하지 않는다

---

### 2.4 로그아웃

- 사용자는 로그아웃할 수 있다
- 로그아웃 시 현재 인증 사용자 소유의 활성 Refresh Token을 무효화한다
- Refresh Token 소유자와 Access Token subject가 일치하는 경우에만 실제 무효화한다
- 이미 만료되었거나 존재하지 않는 Refresh Token이어도 로그아웃 응답은 성공으로 처리할 수 있다
- Access Token 블랙리스트는 현재 필수 범위에서 제외하고 별도 정책으로 결정한다

---

### 2.5 토큰 발급

- 로그인 성공 시 다음 토큰을 발급한다
    - Access Token (짧은 만료 시간)
    - Refresh Token (긴 만료 시간)
- 토큰에는 사용자 식별 정보가 포함되어야 한다

---

### 2.6 토큰 검증

- 모든 보호된 API 요청은 Access Token을 통해 인증한다
- 서버는 JWT 서명을 검증하여 사용자 인증을 수행한다
- 토큰이 만료되었거나 유효하지 않은 경우 요청을 거부한다
- 별도 `/api/v1/auth/token/verify` API를 외부 서비스에 제공할지 여부는 별도 결정한다

---

### 2.7 토큰 재발급

- Access Token 만료 시 Refresh Token을 통해 재발급할 수 있다
- Refresh Token은 Redis에 저장되어야 한다
- Refresh Token은 Token Family와 상태값 기반으로 rotation 한다
- 유효하지 않은 Refresh Token으로 요청 시 재발급을 거부한다
- 이미 사용된 Refresh Token 재사용이 감지되면 Token Family 단위 폐기를 고려한다

---

## 3. 계정 관리

### 3.1 Identity 관리

- 사용자는 하나의 Identity를 가진다
- 하나의 Identity는 여러 로그인 방식과 연결될 수 있다
    - 일반 로그인
    - 소셜 로그인

---

### 3.2 소셜 계정 연동

- 하나의 Identity에 여러 소셜 계정을 연결할 수 있다
- 동일한 소셜 계정은 하나의 Identity에만 연결된다

---

### 3.3 M4 계정 관리

- 사용자는 본인의 정보를 조회할 수 있다
- 사용자는 수신용 이메일과 전화번호를 수정할 수 있다
- 이메일 변경은 인증 완료 후 User.email에 반영되어야 하며 LOCAL Identity.loginId는 변경하지 않는다
- 사용자는 현재 비밀번호 검증 후 비밀번호를 변경할 수 있다
- 사용자는 본인의 계정 상태를 조회할 수 있다
- 사용자는 회원 탈퇴를 요청할 수 있다
- 탈퇴 계정은 로그인과 토큰 재발급이 불가능해야 한다
- 탈퇴 시 개인정보 제거 및 Refresh Token 무효화 정책을 적용해야 한다

---

## 4. 비밀번호 관리

### 4.1 비밀번호 저장

- 비밀번호는 암호화하여 저장한다
- 평문 저장은 금지한다

---

### 4.2 비밀번호 변경

- 사용자는 비밀번호를 변경할 수 있다
- 기존 비밀번호와 동일한 비밀번호 사용 제한 가능
- 비밀번호 변경 이력을 관리할 수 있다

---

## 5. 로그인 이력

### 5.1 로그인 기록

- 로그인 시 이력을 저장한다
- 저장 항목
    - 사용자 ID
    - 로그인 시간
    - 로그인 방식 (일반 / 소셜)
    - IP 주소
    - 성공 여부

---

## 6. 보안 정책

### 6.1 인증 정책

- Access Token은 짧은 만료 시간을 가진다
- Refresh Token은 별도로 관리된다
- 로컬 계정의 loginId와 email은 서로 다른 책임을 가진다
- 로컬 계정의 이메일 변경은 인증 완료 전까지 User.email에 반영하지 않는다

---

### 6.2 확장 고려

- IP 기반 접근 제한
- 토큰 블랙리스트
- 서비스별 로그인 아이디 분리 
  - (통합 로그인 서버)

---

## 7. 별도 결정 항목

- Access Token 블랙리스트
  - 로그아웃 이후 Access Token을 즉시 무효화할지 별도 결정한다
- 토큰 검증 API 외부 제공 여부
  - 내부 서비스 또는 API Gateway에서 직접 호출할 API가 필요한지 결정한다
- 관리자 인증 시스템
- MFA 2차 인증
