# 커밋 규칙 (Commit Convention)

## 1. 개요

본 문서는 프로젝트의 일관된 Git 커밋 메시지 작성을 위한 규칙을 정의한다.  
모든 커밋은 명확한 의도를 전달할 수 있도록 작성해야 한다.

---

## 2. 기본 형식

커밋 메시지는 다음 형식을 따른다.
- 타입: 내용

예:
- `feat: 로그인 API 추가`
- `fix: 토큰 만료 검증 오류 수정`

---

## 3. 커밋 타입

| 타입 | 설명 |
|------|------|
| feat | 새로운 기능 추가 |
| fix | 버그 수정 |
| docs | 문서 수정 |
| refactor | 리팩터링 (기능 변화 없음) |
| test | 테스트 코드 추가/수정 |
| chore | 설정, 빌드, 의존성 등 기타 작업 |
| style | 코드 포맷팅, 주석 등 비즈니스 로직 변경 없는 작업 |

---

## 4. 커밋 메시지 예시

- `feat: 일반 로그인 API 추가`
- `feat: 카카오 로그인 검증 로직 구현`
- `feat: 구글 로그인 연동 추가`
- `fix: refresh token 만료 검증 오류 수정`
- `docs: 프로젝트 초기 문서 작성`
- `refactor: AuthService 책임 분리`
- `chore: application-dev 설정 추가`

---

## 5. 커밋 작성 규칙

- 하나의 커밋에는 하나의 의도를 담는다
- 기능 추가와 리팩터링을 한 커밋에 섞지 않는다
- 의미 없는 메시지(수정, 작업중, test)는 사용하지 않는다
- 커밋 메시지는 가능하면 한국어로 통일한다

---

## 6. 권장 사항

- 커밋 메시지는 짧고 명확하게 작성한다
- 무엇을 했는지보다 “왜 했는지”가 드러나도록 작성한다
- PR 단위에서 의미 있는 작업이 되도록 커밋을 구성한다
- 이슈번호는 달지 않아도 되나 구분이 필요하다 판단이 개인적으로 드는 순간 달아도 무방하다.
