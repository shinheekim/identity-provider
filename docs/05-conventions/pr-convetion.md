# Pull Request 규칙 (PR Convention)

## 1. 개요

본 문서는 프로젝트의 일관된 Pull Request(PR) 작성 및 관리 규칙을 정의한다.  
PR은 코드 변경 이력을 명확하게 남기고, 리뷰를 통해 품질을 보장하기 위해 사용한다.

---

## 2. PR 제목 형식

PR 제목은 다음 형식을 따른다.

```
[타입] 작업명
```

### 예시

- `[feat] 일반 로그인 API 구현`
- `[docs] GitHub 운영 규칙 문서 추가`
- `[fix] 카카오 사용자 식별 오류 수정`

---

## 3. PR 본문 권장 항목

PR 본문에는 다음 내용을 포함하는 것을 권장한다.
1. 단 Issues의 경우 Closed를 붙인다 (종료의경우)
### Issues
- 해당이슈 문서 

### 3.1 작업 목적
- 해당 작업을 진행한 이유를 작성한다

### 3.2 주요 변경 사항
- 핵심 변경 내용을 요약한다

### 3.3 확인 필요 사항
- 리뷰어가 집중해서 봐야 할 부분을 명시한다

### 3.4 테스트 여부
- 테스트 진행 여부 및 방법을 작성한다

---

## 4. PR 최소 규칙

- PR 없이 직접 병합은 금지한다
- 문서 변경도 반드시 PR로 관리한다
- 작은 작업이라도 변경 이력은 PR로 남긴다
- merge는 상대방의 리뷰를 받은 후에 검토를 진행하고 해야한다


---

## 5. 리뷰 및 머지 정책

- 본인 셀프 머지는 불가능하며 승인 받은 후에 가능한다.

- PR을 올리고나서 상대방에게 알람여부와 상관없이 직접 PR을 올렸다는 내용을 전파한다
  - PR을 받은 리뷰어는 48시간안에 리뷰를 진행한다.
  - 리뷰어가 리뷰를 단 24시간안에 해당 답변과 수정방안을 이야기한다.
    - 이때 논의가 필요한 경우 즉시 연락을 통해 빠른시일내에 15분 회의를 진행한다 (여기서 빠른 시일내에는 개인 일정을 비교하여 가능한 제일 빠른 시간을 의미한다)
    - 수정방안이 정해질경우 바로 작업을 시작하여 마무리후 다했을 경우 다시 리뷰 부탁을 보내며 메세지로도 연락한다.
      - 이때의 경우 개인사정이 없는 한 24시간안에 리뷰를 마무리한다.
     
- 주요 기능 변경은 리뷰 후 병합을 해야한다
- 리뷰 의견이 있는 경우 반영 후 머지한다

### 5.1 Merge 커밋 메세지
- Merge는 메세지는 기본 깃 메세지로 진행한다.
  - 단 Develop은 Squash 머지 방식을 이용한다.
  - Main의경우는 일반적인 Marge를 이용한다

---

## 6. 권장 사항

- PR은 가능한 작은 단위로 나눈다
- 하나의 PR에는 하나의 목적을 담는다
- 리뷰가 쉽도록 변경 범위를 명확하게 유지한다
- 커밋 메시지와 PR 내용이 일관되도록 작성한다
